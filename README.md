# SPLAT 04

**Click. Splat. Win. Stay if you want.**

_The future's messiest professional sport._

SPLAT 04 is a fast, slightly top-down multiplayer paintball game dressed up as a tacky 2004
vision of a rich kid's private Miami waterfront sports league. Two teams — Cyan and Magenta —
fight over a single flat arena, **VICE ESTATE 04**, and whoever owns the most floor when the
90-second clock runs out wins the round. Rounds run back to back forever; you can join, leave
and rejoin at any moment.

There is no account, no launcher and no menu. Opening the site drops you straight into a
playable target range, and once you have painted three inflatable targets you are in a live
4v4 arena with bots filling every empty slot.

## Install and run

```bash
pnpm install
```

Development — starts the shared-package watcher, the game server and the Vite client together:

```bash
pnpm dev
```

Then open **http://localhost:5173**. Vite proxies `/api` and `/ws` to the game server on
port 8787.

Production — one build, one service:

```bash
pnpm build
pnpm start
```

Then open **http://localhost:8787**. The Node server serves the built client, `/api/*` and the
`/ws` WebSocket upgrade from the same origin.

Other commands:

```bash
pnpm test        # shared game rules + server unit and integration tests
pnpm typecheck   # all three packages
pnpm smoke       # boots the production build and checks health, index and /ws
pnpm format      # prettier
pnpm icons       # regenerate the PWA icons (also runs as part of the build)
```

## Testing multiplayer with two browsers

1. `pnpm build && pnpm start`
2. Open **http://localhost:8787/play/vice-estate-04** in one window.
3. Open the same URL in a **second window**, ideally a private/incognito one.

Use a private window for the second player. The guest profile lives in `localStorage`, so two
normal windows in the same browser share one guest and will show the same display name — they
are still two separate players on the server, but they are easier to tell apart with separate
profiles.

Both windows land in the same continuous room, and `curl http://localhost:8787/api/health`
reports how many humans are connected:

```json
{ "ok": true, "arena": "vice-estate-04", "rooms": 1, "players": 2 }
```

To play from a phone on the same network, browse to `http://<your-machine-ip>:8787` for the
production server (it binds `0.0.0.0`), or `http://<your-machine-ip>:5173` in development —
the Vite dev server binds all interfaces and prints the LAN URL on startup.

**Note:** Vite serves on `localhost`, which on most machines resolves to IPv6 `::1`. Use
`http://localhost:5173` rather than `http://127.0.0.1:5173`.

**Note:** a browser tab that is not visible pauses its render loop and its input sends, by
design. Two tabs in the _same_ window will therefore look frozen when they are in the
background — use two separate windows placed side by side.

### Testing touch controls

The on-screen sticks appear when the browser reports touch capability or a coarse pointer. So
either:

- open your browser's device/responsive mode and pick a phone preset (this reports both), or
- append **`?touch=1`** to force the touch UI on any device: `http://localhost:8787/?touch=1`

Narrowing a desktop window is deliberately _not_ enough. The stick zones cover most of the
screen, so showing them on a mouse-driven window would take aim away from the cursor.

Left half of the screen is a floating move stick, right half is a floating aim stick that
auto-fires while held, and the large lime button boosts.

## Architecture

```
apps/
  web/       Vite + React + three.js (@react-three/fiber) browser client
  server/    Node HTTP + ws authoritative game server, also serves the built client
packages/
  shared/    types, constants, protocol, arena geometry and the deterministic game math
```

`packages/shared` is the important one: the movement step, firing rules, projectile
simulation, collision, paint-grid stamping, coverage maths and XP calculation all live there
and are imported unchanged by the server, by the client's local prediction, and by practice
mode. There is exactly one implementation of the rules.

**Client structure**

- `src/game/world.ts` — all high-frequency state, deliberately outside React. Components read
  it inside `useFrame`; React state is reserved for UI transitions like round end.
- `src/game/net.ts` — WebSocket client, prediction and reconciliation.
- `src/game/localgame.ts` — the same shared rules run locally, for the target range and for
  the offline practice fallback.
- `src/scene/` — the arena, procedurally generated from primitives.
- `src/ui/` — HUD and overlays, plain CSS.

`Room` takes both its clock and its random source by injection, so the entire server
simulation — bot decisions, shot spread, everything — is reproducible. The tests drive a
90-second round in milliseconds against a fixed clock and a seeded PRNG, which is why
assertions like "bots tag each other over a round" are deterministic rather than statistical.

### Networking model

The server owns everything: positions, movement validation, boost cooldowns, projectile
spawning and simulation, hits, tags, respawns, paint ownership, coverage, the round clock,
team assignment, bots and match results. The client sends only compact input commands.

- Server simulation: **20 Hz**. State snapshots: **10 Hz**. Client input: up to **20 Hz**.
- Remote players are interpolated ~**120 ms** in the past, so other players move smoothly
  between snapshots. Ahead of the newest sample the client holds the last pose rather than
  extrapolating into cover.
- The local player is **predicted**: inputs apply immediately, and every snapshot carries an
  acknowledged input sequence. On receipt the client snaps to the authoritative state and
  replays every unacknowledged input through the same shared step function.
- Projectiles are visually dead-reckoned between snapshots, but the server's result always
  wins for hits, tags and paint.
- Messages are JSON. Every untrusted field is validated and clamped in
  `packages/shared/src/protocol.ts` before reaching the simulation; fire rate, boost cooldown
  and marker ownership are enforced server-side regardless of what a client claims.
- Disconnecting preserves your slot for ~20 seconds and a bot drives it in the meantime.
  Reconnecting with your guest ID and a short-lived token restores the same slot.
- If the socket cannot be established within a few seconds, the client offers
  **Practice with bots**, which runs the same shared rules locally. Practice results are
  labelled local-only and are never presented as online play.

### The paint coverage grid

The playable floor is a **128 x 84** ownership grid (`Neutral` / `Cyan` / `Magenta`), which is
about 0.64 world units per cell across an 82 x 54 arena. Cells sitting under cover are removed
from the paintable mask at startup, so shots that strike a bunker leave a cosmetic splat but
can never move the score. Coverage percentages are computed over paintable cells only —
currently **8,915** of 10,752 cells, or 82.9% of the rectangle.

A projectile impact stamps every paintable cell inside its splash radius, and repainting an
enemy cell transfers ownership. Splat edges are made ragged by a deterministic per-cell hash,
so the same shot produces byte-identical results on server and client.

The server tracks dirty cell indices and sends **compact deltas** — a flat
`[index, owner, index, owner, …]` array — capped at 2,400 cells per snapshot, with any excess
riding the next one. A joining client gets the whole grid once, run-length encoded and
base64'd. At a round boundary the server sends a single `gridReset` instead of thousands of
no-op deltas.

The client renders ownership as one **`DataTexture`** sampled by a custom shader on a single
floor mesh — one draw call, no per-cell meshes. Red channel is Cyan, green is Magenta, and
linear filtering blends them into soft wet paint over the pale terrazzo court. Cyan paint
carries a stripe motif and Magenta a dot motif, so ownership is never communicated by colour
alone.

### Bots

Bots run on the authoritative server and produce exactly the same `PlayerInput` a human client
sends, so they are subject to identical rules. They use a small finite-state machine —
`paint-route`, `hunt`, `defend`, `retreat`, `boost-reposition` — over a navigation lattice of
105 nodes whose every node and edge is validated against the real colliders at startup. Paths
are found with a BFS that runs only when a bot's goal changes, never per frame. Each bot has a
seeded personality: reaction delay, aggression, aim error, preferred lane, marker and how
willingly it spends boost. They are meant to be fun and fallible, not tournament-perfect.

## Known prototype limitations

- **Progression is local only.** XP, Credits and cosmetics live in `localStorage` behind a
  typed `ProfileRepository` seam. Clearing site data loses the guest. Two tabs in the same
  browser share one guest profile.
- **Marker unlocks are self-reported.** The client tells the server its completed match count
  and the server gates the two sidegrades on it. Since progression is local anyway, this is
  trusted; it needs a real account before it means anything.
- **Crews and challenges live in server memory** with a TTL (2 hours and 24 hours). They are
  lost on restart, and on a multi-instance deployment a code would only work on the node that
  issued it. Persistent crews need real storage.
- **One room per process, no matchmaking beyond "join the busiest room with a seat."** There
  is no skill-based matchmaking, no region routing and no room migration.
- **No account system.** The "Claim this player?" prompt after your first round is UI only —
  the email, passkey and wallet buttons are explicitly labelled `Coming later` and do nothing.
- **No anti-cheat beyond server authority and input clamping.** A determined client can still
  send plausible-but-fake inputs at the allowed rate.
- **The claim/highlight card is an image, not a video.** `Copy highlight` renders a 9:16
  canvas you can copy the link for or download as PNG.
- **Assists are approximate** — a team-mate within 14 units who fired in the last 3 seconds.
- **One arena, one mode.** No map rotation, no alternative rulesets.
- Bots are competent at painting and adequate at fighting; they do not coordinate as a team.

## Explicitly not built

No blockchain, wallets, tokens, USDC, staking, prize matches, real-money wagering, a
marketplace, a map editor, voice chat, authentication, database persistence, multiple arenas,
multiple modes, skeletal animation or native apps. `packages/shared/src/ledger.ts` defines an
inert `RewardLedger` interface as a future seam and nothing implements it beyond a no-op.

Only **XP** and **Credits** exist, both non-transferable and local. Nothing in this prototype
can be bought with real money and nothing implies players are earning money.

## Next steps, in priority order

1. **Playtest and retune.** The constants in `packages/shared/src/constants.ts` and the marker
   table are starting points. Landing range and splash radius in particular deserve a session
   with real players.
2. **Server-side progression** behind the existing `ProfileRepository` seam, so marker unlocks
   and Credits mean something and the self-reported match count can be dropped.
3. **Persistent crews and challenges** in real storage, which also unblocks running more than
   one server instance.
4. **Bot team coordination** — lane assignment and a sense of which third is contested, rather
   than each bot scoring nodes independently.
5. **Binary protocol** for snapshots if profiling shows JSON is the bottleneck; the protocol is
   already isolated in `packages/shared/src/protocol.ts`.
6. **Spectator and rejoin polish**: a proper attract camera between rounds and a scoreboard
   that persists across the session.
7. **A second arena**, once the first has been tuned enough to know what the layout rules are.

## Performance notes

The production bundle is roughly **322 KB gzipped** (three.js is the bulk of it), well inside
the 15 MB budget. The arena is built from shared primitive geometries and a nine-material
library; paint is one dynamic texture and one draw call; projectiles and cover splats are
fixed-size `InstancedMesh` pools that never grow. Device pixel ratio is capped at 2, shadows
and antialiasing are disabled on the low-quality path, and an FPS sampler switches quality
automatically when `Quality: Auto` is selected. Rendering and input sends pause when the tab is
hidden.

Settings (Esc) exposes quality, sound, haptics, aim-assist strength, reduced motion, high
contrast and announcer speech. Aim assist only curves paintballs that were already within 6
degrees of on-target, and spends a bounded budget so it can never feel automatic.

## Accessibility

Menus are keyboard navigable with visible focus states and real `<button>` elements. Team
ownership is never colour-only: Cyan uses stripes and a forward wedge, Magenta uses dots and a
round pip, on the floor, on the score bar and under each player. Reduced motion is honoured for
camera easing and UI animation, touch targets are thumb-sized, and opening the settings overlay
releases gameplay input so the page never eats keystrokes.
